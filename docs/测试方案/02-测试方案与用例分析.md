# 测试方案与用例分析

测什么层、核心场景怎么想用例、钱和单子怎么对、哪些先测。**读完本文你能**：说清测试分层和优先级、给定场景能写出用例思路、讲清「怎么做交易所测试」、「钱错了怎么排查」

---

## 一、测试分几层做

| 层 | 测啥 | 咋测 | 重点 |
|----|------|------|------|
| 单元/组件 | 撮合、算价、手续费、风控规则 | 单测、Mock 依赖 | 规则算对、边界和异常 |
| 接口 | 下单/撤单/查单、充值回调、提现、行情 | 接口自动化、契约 | 入参校验、状态码、关键字段、幂等 |
| 业务场景 | 一整条：注册→充值→下单→成交→提现、划转 | 场景用例、主路径 | 状态别乱、余额和流水对得上 |
| 一致性/对账 | 余额和流水、订单和成交、DB 和缓存和推送 | 对账脚本、数据校验 | 钱平、没漏单错单 |
| 性能与稳定 | 下单撤单查询扛多少、撮合多慢、推送多慢 | 压测、混沌 | 限流、降级、熔断别崩 |

## 二、核心场景怎么设计用例

### 资产与钱

- **充值**：正常入账、同一笔 tx 来多次只入一次、确认数不够/够了、错币种错地址、金额精度。
- **提现**：正常扣款并发 tx、余额不够、超限额、地址格式和黑名单、手续费扣了到账多少。
- **划转**：划完总资产不变（除了手续费）、可用和冻结算对、并发划转别把余额搞乱。
- **流水**：有变动就有流水、用流水能反推余额、流水类型和业务对上。

举例：同一笔充值 tx 回调多次，只入账一次、只一条流水；提现扣多少和链上发多少一致，失败要把钱加回去并记流水。

### 订单与撮合

- **下单**：价格数量精度、最小下单量、余额和冻结够不够、交易对能不能用、限价挂上、市价立刻吃单或部分吃。
- **撤单**：已报的能撤、部分成交的撤掉未成交部分、重复撤当幂等、没有的订单别乱撤。
- **撮合**：价格时间优先、成交价和量对、买卖两边余额和持仓跟着变、订单状态和成交记录一致。

举例：限价单挂上后冻结变多，撤掉后冻结要放出来；市价全成后订单是「全部成交」，两边余额和成交记录对上。

### 风控与限额

- 单笔/单日提现限额、笔数、大额再验证。
- 黑名单地址/用户不能提或不能交易。
- **熔断**：行情太猛或错误率超阈值时停交易或只让撤单。
- **降级**：压力大或依赖挂掉时关非核心（如关行情推送、只保交易和查余额），保核心不崩。

举例：提到日限额了，再提就拒，错误码说清楚；黑名单地址提现直接拒，不扣钱；熔断触发后新单拒、撤单通；降级后该关的接口返回降级提示、核心下单撤单查余额仍可用。

### 降级与熔断能力（测什么、怎么测）

| 能力 | 是啥 | 测啥 | 怎么测 |
|------|------|------|--------|
| **熔断** | 达到条件（涨跌幅、波动率、错误率等）时缩小或暂停交易范围 | 触发后新单拒/只许撤单、恢复后正常 | 造触发条件（模拟行情或错误率）→ 调下单/撤单接口断言行为；改回条件 → 断言恢复后可下单 |
| **降级** | 压力或依赖异常时关非核心功能、保核心 | 降级开关开后，非核心不可用或限流、核心仍可用；恢复后功能回来 | 开降级开关（或模拟依赖超时）→ 断言行情/次要接口不可用或限流、下单撤单查余额可用；关开关 → 断言全部恢复 |

**注意**：熔断是「到线就停一块」；降级是「主动关一部分保另一部分」。压测和混沌时要验证：限流、熔断、降级在高压或依赖故障下真的生效，且不会误伤核心路径。

### 测试策略怎么讲（面试/汇报时用）

别人问「你怎么做交易所测试」时，可以按下面结构说，一分钟内讲完：

1. **分层**：单元测撮合/算价/风控规则；接口测下单撤单查询、充值提现回调，重点幂等和限流；场景测整条链路（注册到提现）；对账测余额与流水、订单与成交、DB 与缓存一致；再压测和混沌看限流、熔断、降级是否生效。
2. **核心原则**：交易所核心是「钱和单子不能错」，所以优先保资金和订单一致性，P0 是钱错、单子错、提现错，再补限额风控和体验。
3. **对账**：余额 = 昨日余额 + 流水汇总；订单成交汇总和成交表对上；冻结和未成交挂单对上；有唯一业务单号和状态，方便对账和排查。
4. **质量门禁与准出**：发布前设质量门禁（如 P0/P1 清零、核心用例与回归通过、对账无差异）；准出标准与发布红线共识，不达标不发布；质量左移（需求评审、冒烟通过才提测）；大版本/大促前全链路压测，结果纳入准出。

### 用例设计示例（给定场景怎么写）

**场景**：用户充值，链上同一笔 tx 的回调被重复推送 3 次。

- **预期**：只入账 1 次，流水 1 条，余额只加一次。
- **用例**：构造重复回调（同一 txHash、同一金额），调用入账接口 3 次；断言余额增加等于 1 倍金额、流水表只有 1 条该 tx 记录、接口返回或幂等标识正确。
- **边界**：txHash 为空、金额为 0、确认数不足已入账/未入账分支。

**场景**：合约用户保证金率跌到强平线。

- **预期**：触发强平，仓位平掉，盈亏结算进余额，流水有强平记录。
- **用例**：造数据使**标记价**（不用最新价，防插针）算出的保证金率等于阈值；触发清算任务或调强平接口；断言仓位为 0、余额变化等于强平盈亏、流水类型为强平；再测略高于阈值不强平、略低于阈值强平。
- **边界**：强平单部分成交、穿仓时风险金扣减；**插针**场景下若误用最新价会误爆，要验证强平取价是标记价/指数价且限幅。

**场景**：合约加仓、减仓。

- **预期**：加仓后持仓量增加、占用和开仓均价重算正确；减仓后持仓量减少、释放保证金和实现盈亏进余额、剩余持仓占用与强平线重算正确。
- **用例**：先开仓再同方向加仓，断言持仓量、占用、开仓均价与手工计算一致；再部分减仓，断言释放保证金、实现盈亏、剩余持仓的占用与强平线；最后平仓，断言仓位为 0、流水完整。
- **边界**：加仓后杠杆/限额是否允许、减仓为 0 即平仓、减仓数量超过持仓的拒绝。

## 三、数据一致性与对账

### 要对上的几件事

| 对啥 | 啥意思 | 咋校验 |
|------|--------|--------|
| 余额 | 账户余额 = 之前余额 + 流水汇总 | 定时跑对账 |
| 订单和成交 | 订单上的成交汇总 = 成交表里这条订单的汇总；状态和成交能对上 | 按订单对 |
| 冻结和挂单 | 某币种冻结 = 这个币种所有未成交挂单占用的和 | 余额和订单对 |
| 链上和内部 | 提现发的 tx 和链上查到的一致；充值入账和链上确认一致 | 链上查和内部流水比 |

### 好测一点需要啥

- 订单、成交、流水都有唯一业务单号，对账和查问题好用。
- 下单、撤单、成交、充值、提现都有清晰状态和时间。
- 有对账或报表接口/导出，方便自动化跑。

## 四、先测啥后测啥（优先级）

- **P0**：钱错了（多扣、少入、重复入）、订单和成交对不上、提现地址或金额错。
- **P1**：余额和流水对不上、撮合价量错、限额/风控没拦住。
- **P2**：页面上和后台不一致、推送慢或丢、次要路径报错不友好。

设计用例先保住 P0，再按回归和发版节奏补 P1、P2。

### 质量门禁与准入准出（大厂常见做法）

用**质量门禁**把「不达标就不发布」固化到流程里，避免带病上线；**准入**管「能开始测的条件」，**准出**管「能发布的条件」。

| 概念 | 含义 | 常见做法（交易所可照搬） |
|------|------|---------------------------|
| **质量门禁** | 发布前必须通过的检查项，不通过则卡住发布 | P0/P1 缺陷清零、核心用例通过、自动化回归通过、关键对账无差异、无未关闭的发布红线问题 |
| **准入标准** | 提测/开始测试的前提 | 需求评审通过、冒烟用例通过、环境就绪、核心接口可调；不满足不准入，避免无效测试 |
| **准出标准** | 允许上线的条件 | 满足质量门禁、无发布红线、回归通过、产品/测试签字；重大活动前可加全链路压测通过、灰度观察无异常 |
| **发布红线** | 一旦触发必须拦停发布的问题类型 | 如：资金/订单类 P0 缺陷、对账不平、核心接口失败率超阈值、未修复的已知重大风险；红线问题不关闭不发布 |
| **质量左移** | 提前发现问题的实践 | 需求/设计阶段参与评审、接口契约先行、单测与静态检查、提测前开发自测与冒烟；减少缺陷逃逸到测试/线上 |
| **全链路压测** | 在接近线上的链路上做压测 | 订单→支付→清算/对账整条链压测，验证限流/降级/熔断与容量；大促或大版本前执行，结果作为准出参考 |
| **质量度量/大盘** | 用数据看质量趋势 | 缺陷密度、逃逸率、自动化覆盖率、回归通过率、线上故障与复盘；用大盘驱动改进和门禁阈值 |

**落地要点**：门禁项与准出标准写入发布流程（如 CI 卡点、发布审批单）；发布红线在项目内共识并录入缺陷类型；质量左移靠流程约定（评审参与、冒烟通过才提测）；全链路压测按发版节奏做，结果纳入准出。

### 钱错了 / 单子错了怎么排查（思路）

- **余额不对**：先对账——当前余额是否等于「上一时点余额 + 期间流水汇总」；若不等，查流水是否漏记、重复记、方向反；再查是否冻结算错（未成交挂单占用）。
- **订单和成交对不上**：按订单 ID 汇总成交表，看是否等于订单上的已成交量、状态是否一致；若不等，查是否漏推成交、重复成交、撤单后仍成交。
- **提现扣了钱链上没发**：查提现单状态、链上 tx 是否失败、是否进了重试；若链上失败，余额是否回滚并记流水。
- **强平后仓位还在**：查强平任务是否执行、强平单是否进撮合、是否部分成交未处理；查标记价/指数价是否取错导致未到线误判。

### 链上不可逆：真有 bug 怎么处理

区块链上交易一旦确认就**不能改、不能撤**，所以测试和设计要围绕「少出错」和「出错了能兜底」。

**事前（预防）**

- **测试**：主网前在测试网 / 私链充分测；提现、合约调用等关键路径做单测 + 接口 + 场景 + 对账；大额或敏感操作加人工/多签复核。
- **设计**：提现支持白名单、单笔/单日限额、大额延迟到账（给窗口期拦截）；合约能升级的用代理模式、必要时加 pause；关键参数多签或时间锁，避免一次改错全崩。
- **对账与告警**：链上余额与内部账定期对账；异常大额、异常地址、失败率突增等告警，便于在「更多笔错」之前发现问题。

**事后（已经上链了）**

- **链上本身**：交易不可回滚。合约若有 bug，若设计了可升级 / pause，可以暂停或换实现；若没有，只能认损或极端情况下考虑 fork（非常少见）。
- **交易所 / 业务侧**：错发、多发、发错地址等，链上改不了，只能**业务兜底**：用风险准备金或自有资金给用户补足；发错地址的尝试联系对方协商（多数无果）；事后复盘、修 bug、加校验和限额，避免再犯。
- **流程**： incident 响应（止损、通知用户）、对账确认影响范围、补偿方案、post-mortem、修复与回归、补充用例和监控。

**测试能做的**：把「不可逆」当约束，在用例里强调：提现前校验地址与金额、重复请求幂等、大额与敏感操作有二次确认或限流；设计上尽量让「错也只错在链下」，链下可回滚、可补款，链上尽量少做不可逆操作，或先小范围再放大。**熔断/降级**也是兜底：异常时熔断可暂停交易、降级可关非核心保核心，测试要验证触发条件和恢复后行为。

## 五、和本仓库的对应关系

本仓库有链上接口自动化（JSON-RPC、Web3）和「合约 getStats 和链上 get_balance 一致性」的校验，思路可以直接搬到交易所：

- 接口层：就像「RPC 和 Web3 结果要一致」，换成「下单/查询接口和 DB、缓存要一致」。
- 一致性：就像「合约余额和链上余额对上」，换成「账户余额和流水汇总对上」「订单状态和成交对上」。

交易所核心就是「钱和单子别错、数要对得上」，分层测 + 对账脚本把这几块兜住就行。撮合、杠杆、清算、风控在业务上咋回事、测的时候盯啥，见 [01-交易所业务场景梳理](./01-交易所业务场景梳理.md) 第四节。

## 六、一分钟说清「我怎么做交易所测试」（表达要点）

- **分层**：单测规则、接口测幂等和限流、场景测整条链路、对账测余额/流水/订单一致、压测看限流熔断降级。
- **优先级**：P0 钱错、单子错、提现错；P1 余额流水对不上、撮合错、风控没拦住；P2 展示和体验。
- **对账**：余额和流水对上、订单和成交对上、冻结和挂单对上；有业务单号和状态，能还原和排查。
- **举例**：充值幂等、强平线到线就平、资金费方向对、限额到限就拒；钱错了先对账流水再查冻结和订单。
- **质量门禁**：发布前 P0/P1 清零、核心与回归通过、对账无差异；准出与发布红线共识，不达标不发布；质量左移 + 全链路压测作为大版本/大促准出参考。

能按上面五点说完，对方会认为你有清晰的测试思路和大厂级质量意识。
