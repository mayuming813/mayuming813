# 测试方案与用例分析

测什么层、核心场景怎么想用例、钱和单子怎么对、哪些先测。

---

## 一、测试分几层做

| 层 | 测啥 | 咋测 | 重点 |
|----|------|------|------|
| 单元/组件 | 撮合、算价、手续费、风控规则 | 单测、Mock 依赖 | 规则算对、边界和异常 |
| 接口 | 下单/撤单/查单、充值回调、提现、行情 | 接口自动化、契约 | 入参校验、状态码、关键字段、幂等 |
| 业务场景 | 一整条：注册→充值→下单→成交→提现、划转 | 场景用例、主路径 | 状态别乱、余额和流水对得上 |
| 一致性/对账 | 余额和流水、订单和成交、DB 和缓存和推送 | 对账脚本、数据校验 | 钱平、没漏单错单 |
| 性能与稳定 | 下单撤单查询扛多少、撮合多慢、推送多慢 | 压测、混沌 | 限流、降级、熔断别崩 |

## 二、核心场景怎么设计用例

### 资产与钱

- **充值**：正常入账、同一笔 tx 来多次只入一次、确认数不够/够了、错币种错地址、金额精度。
- **提现**：正常扣款并发 tx、余额不够、超限额、地址格式和黑名单、手续费扣了到账多少。
- **划转**：划完总资产不变（除了手续费）、可用和冻结算对、并发划转别把余额搞乱。
- **流水**：有变动就有流水、用流水能反推余额、流水类型和业务对上。

举例：同一笔充值 tx 回调多次，只入账一次、只一条流水；提现扣多少和链上发多少一致，失败要把钱加回去并记流水。

### 订单与撮合

- **下单**：价格数量精度、最小下单量、余额和冻结够不够、交易对能不能用、限价挂上、市价立刻吃单或部分吃。
- **撤单**：已报的能撤、部分成交的撤掉未成交部分、重复撤当幂等、没有的订单别乱撤。
- **撮合**：价格时间优先、成交价和量对、买卖两边余额和持仓跟着变、订单状态和成交记录一致。

举例：限价单挂上后冻结变多，撤掉后冻结要放出来；市价全成后订单是「全部成交」，两边余额和成交记录对上。

### 风控与限额

- 单笔/单日提现限额、笔数、大额再验证。
- 黑名单地址/用户不能提或不能交易。
- 熔断：行情太猛时停交易或只让撤单。

举例：提到日限额了，再提就拒，错误码说清楚；黑名单地址提现直接拒，不扣钱。

## 三、数据一致性与对账

### 要对上的几件事

| 对啥 | 啥意思 | 咋校验 |
|------|--------|--------|
| 余额 | 账户余额 = 之前余额 + 流水汇总 | 定时跑对账 |
| 订单和成交 | 订单上的成交汇总 = 成交表里这条订单的汇总；状态和成交能对上 | 按订单对 |
| 冻结和挂单 | 某币种冻结 = 这个币种所有未成交挂单占用的和 | 余额和订单对 |
| 链上和内部 | 提现发的 tx 和链上查到的一致；充值入账和链上确认一致 | 链上查和内部流水比 |

### 好测一点需要啥

- 订单、成交、流水都有唯一业务单号，对账和查问题好用。
- 下单、撤单、成交、充值、提现都有清晰状态和时间。
- 有对账或报表接口/导出，方便自动化跑。

## 四、先测啥后测啥（优先级）

- **P0**：钱错了（多扣、少入、重复入）、订单和成交对不上、提现地址或金额错。
- **P1**：余额和流水对不上、撮合价量错、限额/风控没拦住。
- **P2**：页面上和后台不一致、推送慢或丢、次要路径报错不友好。

设计用例先保住 P0，再按回归和发版节奏补 P1、P2。

## 五、和本仓库的对应关系

本仓库有链上接口自动化（JSON-RPC、Web3）和「合约 getStats 和链上 get_balance 一致性」的校验，思路可以直接搬到交易所：

- 接口层：就像「RPC 和 Web3 结果要一致」，换成「下单/查询接口和 DB、缓存要一致」。
- 一致性：就像「合约余额和链上余额对上」，换成「账户余额和流水汇总对上」「订单状态和成交对上」。

交易所核心就是「钱和单子别错、数要对得上」，分层测 + 对账脚本把这几块兜住就行。
